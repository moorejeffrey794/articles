# 用 saga 编排退款的跨服务事务

<!-- content-workspace-job:f5276d9f-9e21-4378-b061-55c1a30f2d32 -->

## 问题场景

退款下单要跨订单、库存、支付三个服务，用本地事务包不住。中间某一步失败后，前面已经扣掉的库存没人释放，数据就对不上了。

## 实现步骤

把流程拆成若干本地事务，每一步都实现对应的补偿操作。

```java
try {
    orderService.create(o);
    stockService.lock(o);
    payService.charge(o);
} catch (Exception e) {
    payService.refund(o);
    stockService.unlock(o);
    orderService.cancel(o);
}
// 预期：控制台输出与上文描述一致
```

失败时按逆序执行已成功步骤的补偿，注意补偿本身也可能失败。

```java
void compensate(Runnable step, String key) {
    if (done.add(key)) {
        step.run();
    }
}
```

补偿必须幂等，重复执行不能产生副作用，否则重试会越补越乱。

```java
System.out.println(done.size());
System.out.println(done.contains("refund"));
```

## 验证方法

人为让支付步骤失败，库存应被释放、订单应变为已取消，最终数据一致。

## 注意事项

saga 没有隔离性，中间状态对外可见，需要业务上容忍或用状态机控制；补偿失败要有兜底对账，不能只靠重试。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
