# 排查运单表写入时的死锁与重试

## 问题场景

运单表的批量任务偶尔报 Deadlock found，重跑又能过。日志里只有一句报错，不知道是哪两条语句互相等待。

## 实现步骤

先看引擎状态里的最近一次死锁详情，能看到两个事务各持有什么锁、在等什么锁。

```sql
SHOW ENGINE INNODB STATUS\G
```

查当前锁等待关系，确认是否还有正在僵持的事务。

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

把事务里的访问顺序统一，比如都按主键升序更新，能从根上消除大部分死锁。

```sql
SELECT trx_id, trx_state, trx_query
FROM information_schema.innodb_trx;
```

## 注意事项

死锁是数据库的正常保护机制，应用层仍要有重试；重试要加随机退避，否则同时重试会再次撞在一起。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确保线上行为始终可控。

在多人协作的项目里，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

在压测阶段，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。
