# 用 outbox 模式保证设备事件不丢

<!-- content-workspace-job:2d189513-a0e0-47e6-b6c9-4bad8ea858c1 -->

## 问题场景

设备下单后要发消息通知下游，代码里先写库再发 MQ。中间进程崩溃，库里有了订单但消息没发出去，下游永远收不到。

## 实现步骤

在业务表旁边建一张 outbox 表，与业务写入放在同一个事务里。

```sql
INSERT INTO outbox (id, topic, payload, status)
VALUES (?, ?, ?, 'new');
```

独立线程轮询未投递的记录，发送成功再标记，失败保留待重试。

```java
@Transactional
public void place(Device o) {
    repo.save(o);
    outbox.save(event(o));
}
```

多实例轮询时用 SKIP LOCKED 避免重复取同一条。

```sql
SELECT id, payload FROM outbox
WHERE status = 'new' ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;
```

## 注意事项

outbox 表会持续增长，要配定期清理；下游必须能处理重复消息，至少一次投递无法保证只发一次。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在多人协作的项目里，应当限定作用范围避免影响其他业务，保证每一步都可验证。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。
