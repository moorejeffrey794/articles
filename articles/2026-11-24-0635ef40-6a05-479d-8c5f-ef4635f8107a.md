## 问题场景

每次渲染单品详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["margin"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

结合团队现状，可以通过压测确认容量水位，避免资源被长期占用。

上线初期，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。
