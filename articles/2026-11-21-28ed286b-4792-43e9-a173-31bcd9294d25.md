# 账户表深分页查询改用延迟关联

<!-- content-workspace-job:28ed286b-4792-43e9-a173-31bcd9294d25 -->

## 问题场景

账户表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM accounts WHERE credit > 400 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM accounts a
JOIN (SELECT id FROM accounts WHERE credit > 400
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM accounts a
JOIN (SELECT id FROM accounts ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

在多人协作的项目里，应当限定作用范围避免影响其他业务，同时把结论沉淀进团队文档。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在实际落地时，应确认依赖版本与运行环境一致，防止出现隐性回归。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。
